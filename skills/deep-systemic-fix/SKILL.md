# Deep Systemic Fix

## 默认策略

- 修复问题的默认目标是消除根因和同类失效路径，而不是增加一层症状补丁。
- “更深入”不等于扩大范围。修复应落在正确的抽象层，同时保持改动聚焦于当前问题。
- 优先修正错误的契约、状态生命周期、分层边界或数据流，而不是要求调用方绕过错误实现。
- 最小安全补丁只用于必须立即控制的安全、数据损坏或生产中断风险。止血后应在同一任务中继续完成持久修复，并明确哪些部分是临时措施。
- 不以牺牲安全性、权限、数据一致性、可回滚性或可维护性来换取表面上的“彻底”。

## 调查要求

1. 复现或准确确认实际行为，区分症状、触发条件和根因。
2. 追踪完整生命周期，而不只检查当前成功路径：
   - 创建、初始化或首次调用
   - 正常执行路径
   - 恢复、重载、重试和恢复流程
   - 兼容迁移、版本切换和模型切换
   - 持久化、缓存失效和错误路径
3. 判断问题归属层级：协议契约、状态管理、数据模型、缓存、并发时序、提示词或 UI 展示。
4. 搜索同类临时补丁、重复逻辑和过时兼容代码，避免只修一个调用点。
5. 以生成类型、官方文档、实际实现或运行时行为作为事实来源，不依据字段名称猜测语义。

## 实现要求

- 在问题所属层级修复。契约错误时，不要通过调用方重复兜底来掩盖。
- 多条入口共享同一不变量时，将修复集中到共享层，并覆盖所有入口。
- 根因修复完成后，移除不再需要的临时补丁、提示词补丁、重复兼容分支和死代码。
- 若必须修改公共 API、状态结构或持久化格式，同时更新所有生产者、消费者、迁移逻辑和相关文档。
- 不用吞异常、增加延时、盲目重试或追加提示词来隐藏失败。
- 保留用户已有的无关改动，不借机重构无关代码。

## 验证要求

- 为根因和关键边界路径增加回归测试，尤其是首次调用与重复调用、恢复后调用、模式切换和兼容恢复路径。
- 条件允许时，增加一个在旧实现上失败、在新实现上通过的测试。
- 先运行最相关的测试，再运行关联范围测试、类型检查、Lint、格式检查和构建。
- 检查最终差异中是否仍有临时措辞、重复补丁、被破坏的既有行为或未覆盖的调用路径。
- 最终说明根因、为什么该方案是系统性修复、覆盖了哪些路径、完成了哪些验证，以及仍存在的风险。

## 完成标准

- 已解释根因，而不只是描述现象。
- 已覆盖所有相关生命周期和入口路径。
- 临时补丁已移除，或明确标注必要性与退出条件。
- 已有测试基础设施时，已补充针对根因的回归测试。
- 相关验证已通过。
- 未引入无关改动。
